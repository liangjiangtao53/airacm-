## Vision

### 10x Check

Users should be able to open Maintenance Wing from WeChat and continue the same learning, exam, wrong-question, review, forum, and education flows without installing an APK. Android App, H5, and WeChat Mini Program share one student codebase, one backend, one account, and one set of learning records.

### Backend Boundaries

- Add one `WechatMiniProgramService` responsible only for `code2Session`, content-security access-token caching, error normalization, timeout, and redacted logs. Do not split login and moderation into separate provider services.

## Account Model

### Migration

1. Add `registrationSource` to `user`: `key`, `register`, or `wechat`.
2. Add a new nullable `wechatOpenid` column. The first release does not repurpose or clear the legacy `openid` column.
3. Run a read-only preflight before DDL: report duplicate real openids, malformed values, and users whose inferred source conflicts with access-key ownership. Abort the migration if any conflict exists.
4. Backfill `registrationSource=key` where the current `openid` starts with `key:` or the user owns an access key.
5. Backfill `registrationSource=wechat` for legacy real WeChat identities and `register` otherwise.
6. Copy only validated, non-`key:*` legacy identities into `wechatOpenid`.
7. Add a unique nullable constraint for `(tenantId, wechatOpenid)` after the preflight and backfill succeed.
8. New code reads and writes `wechatOpenid`; legacy `openid` remains unchanged so the previous release can be redeployed safely.
9. Remove or repurpose the legacy field only in a later, separately backed-up migration after the mini program has been stable for at least one release cycle.
10. Preserve existing user IDs, access-key ownership, wallets, learning history, and exam history.

### Binding Rules

- One WeChat identity can bind one user; one user can bind one WeChat identity.
- An unbound WeChat login creates a database-backed, one-use, five-minute binding session. The client receives only a random opaque token; the database stores its hash, WeChat identity, expiry, consumed time, and failed-attempt count.
- Binding-session state survives backend restarts, supports immediate revocation, and is consumed in the same transaction as a successful bind.
- Expired and consumed binding sessions are deleted by a bounded scheduled cleanup; normal login never scans the full table.
- A used card binds the user already associated with that card.
- An unused card follows the current App profile-completion flow, then activates the card and binds WeChat in one transaction.
- Password binding validates the existing phone/password account.
- Binding failure must not consume a card or partially update a user.
- Only Admin can unbind. Unbinding removes only the WeChat identity and keeps all user data and entitlement.
- Global single-session behavior remains unchanged. Logging into the mini program invalidates the previous student session.

## Entitlement Rules

- A key-origin user logging in with WeChat must still have an active, non-revoked key.
- The issued token cannot outlive the key expiry time.
- Extending the key takes effect on the next login.
- An expired draft is retained. After renewal, the user can continue it.
- Password-registration users retain the current normal JWT expiry behavior.

## Exam Draft Design

Use the existing `exam_attempt.answers` column for in-progress answers and extend the attempt with:

- `draftVersion` for last-write-wins protection.
- `draftHash` for idempotent retry detection.
- `currentQuestionIndex` for resume position.
- `updatedAt` for stale-attempt diagnostics.
- `activeKey`, set to `active` only while the attempt is current, with a unique constraint on `(tenantId, userId, activeKey)`.
- `abandonedAt` as a nullable timestamp. Keep the existing status values for first-release rollback compatibility.

Rules:

- Only one active attempt is allowed per user. Concurrent starts are serialized and the database unique constraint is the final guard; a loser returns the existing active attempt instead of creating another.
- The client saves locally immediately.
- The client synchronizes at most once every three seconds with small jitter.
- `onHide`, explicit exit, and submit trigger a final flush.
- Draft updates use an atomic compare-and-swap update. They require an in-progress, non-abandoned attempt and a strictly newer client version.
- A retry with the same version and matching `draftHash` returns success. The same version with different content returns `409 Conflict` and reloads the server draft.
- A lower draft version cannot overwrite a newer version.
- Re-entering the exam restores category, locked question order, answers, and current position.
- Starting over requires confirmation and atomically sets `abandonedAt` and clears `activeKey` before creating a replacement.
- Abandoned attempts do not appear in exam review and do not affect scores.
- Submit locks the attempt row, includes the client's final answers, grades once, sets `status=submitted`, and clears `activeKey` in one transaction.
- A delayed draft update cannot modify a submitted or abandoned attempt. Repeating submit returns the already stored result instead of grading twice.

## Content Security

This section applies to the retained H5 and Android App UGC flows. MP-WEIXIN does not expose or compile forum and question-comment submission.

- Check forum topics, forum replies, and question comments before persistence.
- A rejected item is not saved or published.
- The user sees a neutral request to revise the content.
- Do not store the rejected original text in error or audit logs.
- Log only user ID, content type, time, provider result ID, and normalized error code.
- If the content-security provider is unavailable, block publication and preserve the client draft for retry.
- Cache the WeChat access token and refresh it before expiry with a single-flight lock.

## Screenshot Protection

- Restore the default visual effect when leaving protected flows if required by the runtime behavior.
- Apply protection to study, exam, exam review, and wrong-question detail pages.

## Error and Rescue Registry

| Code path | Failure | Rescue | User impact | Logged |
|-----------|---------|--------|-------------|--------|
| `wx.login` | Client network or WeChat failure | Obtain one fresh code and retry once | Can use card/password login | Redacted |
| `code2Session` | Timeout, expired code, provider error | Fail closed; never create a user | Clear retry message | Error code and latency |
| Binding session | Expired, replayed, or too many failures | Reject and restart WeChat login | User repeats login | Session ID only |
| Card binding | Invalid, expired, used concurrently | Transaction rollback | Card remains unchanged | Redacted failure |
| Account binding | WeChat/user already bound | Reject; Admin-only unbind path | Contact Admin | Audit event |
| Content security | Provider unavailable | Reject publication; keep local draft | Retry later | Error code only |
| Content security | Content rejected | Do not persist | Revise content | Result ID only |
| Draft sync | Offline or timeout | Keep local draft; retry later | Answering remains responsive | Aggregated failure |
| Draft sync | Older request arrives late | Atomic CAS rejects old version | No visible impact | Conflict counter |
| Exam start | Concurrent start requests | Unique active key returns existing attempt | One active exam | Conflict counter |
| Exam submit | Retry or delayed draft races submit | Row lock, idempotent result, status guard | One final score | Request ID |
| Exam restore | Local cache damaged | Load server draft | Small loading delay | Warning |
| Exam submit | Final sync/submit fails | Keep local and server draft | Retry submit | Request ID |
| Key expiry | Expired or revoked | Deny new login; retain draft/data | Renew then continue | Login denial |

## API Plan

- `POST /auth/wechat/bind/key`: bind with an access key; complete profile when needed.
- `POST /auth/wechat/bind/password`: bind an existing password account.
- `DELETE /admin/users/:id/wechat-binding`: Admin-only audited unbind.
- `GET /exams/active`: load the current in-progress attempt.
- `PUT /exams/:id/draft`: atomically save versioned answers, hash, and current index; return `409` for a real conflict.
- `POST /exams/:id/abandon`: confirm abandonment.
- Existing forum and question-comment create APIs invoke content security internally for H5 and Android App; MP-WEIXIN does not compile their client methods.

### Database Contract

`user` additions:

- `registrationSource varchar(16) not null default 'register'`.
- `wechatOpenid varchar(128) null`.
- Unique index `(tenantId, wechatOpenid)`. MySQL InnoDB permits multiple `NULL` values in a unique index, so unbound users do not conflict.

`wechat_bind_session` additions:

- UUID primary key, tenant ID, SHA-256 token hash, WeChat openid, expiry, consumed timestamp, failed-attempt count, and created timestamp.
- Unique token-hash index plus expiry index. Never store the plaintext opaque token.
- Cleanup is opportunistic and bounded: at most once per minute per API instance and at most 100 expired/consumed rows per batch. Do not add a scheduler dependency for this table.

`exam_attempt` additions:

- `draftVersion integer not null default 0`.
- `draftHash char(64) not null default ''`.
- `currentQuestionIndex integer not null default 0`.
- `activeKey varchar(16) null`.
- `abandonedAt datetime null`.
- Updated timestamp.
- Unique index `(tenantId, userId, activeKey)`. Active attempts use `activeKey='active'`; submitted and abandoned attempts set it to `NULL`.

### Migration Units

1. Add user identity columns and the binding-session table. This migration is additive only.
2. Backfill registration source and validated legacy real openids, then add the WeChat identity unique index. Run duplicate/malformed/source-conflict preflight before backfill and again before the unique DDL. Backfill statements are idempotent so a MySQL DDL failure can be retried safely.
3. Add exam draft columns and the active-attempt unique index. Before adding the index, report and resolve any existing duplicate in-progress attempts deterministically by keeping the newest and marking older rows abandoned.

MySQL DDL is not treated as transactionally reversible across the full migration chain. Rollback means disabling the feature and redeploying the previous application, while leaving additive columns in place. Database restore is used only for a verified data-corruption event with explicit approval.
